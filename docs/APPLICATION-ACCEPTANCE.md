# Installed application acceptance

The completed eight-check disposable hosting report establishes hosting/runtime availability for the reported host run. Application acceptance is the next step. Use dedicated test domains so useful application data can be retained for later login, persistence and restore drills.

1. Update DevOne through Software Updates.
2. In Websites & files → Install an app, install WordPress on a new test domain or empty PHP 8.3 site. The Owner approves the installer and its prerequisites/database with password/MFA.
3. Install DevOne CMS · preview on a separate test domain or empty stopped Node.js 22 site. This is the alpha.4 foundation, not a stable/full CMS product.
4. Point the domains at the server and issue HTTPS using the website controls.
5. Open QA Center → Installed application checks. Refresh apps, choose a site, and run read-only app checks. Each report identifies its domain/time, actual checks and outstanding acceptance requirements. Results are held in the dashboard session and cleared on refresh; there is no durable application-acceptance history yet.
6. Separately reveal the initial administrator credentials through the existing fresh Owner password/MFA confirmation. Log into the application over HTTPS. Real login/content writes, restart persistence and backup/restore acceptance still require their own evidence; the read-only report cannot certify them.

The verifier never accepts a caller URL, file path, command or secret. The selected site must come from the Agent registry and have a managed WordPress/CMS installation. Probes use fixed GET paths and loopback connections, the registered Host header, and trusted HTTPS certificate validation/SNI when TLS is configured. No redirects, public DNS resolution, Cloudflare account access, administrative login, app content writes or resource deletion are performed. Bounds are three seconds and 512 KiB per request, with a single Agent verification at a time and an API start-rate limit. API access is Owner-only, uncached; check requests require the panel Origin. Audit entries contain only the site ID and read-only scope.

WordPress checks require its front page, real login form and denial of wp-config.php. CMS checks require the active managed service, product/version health, initialization matching the domain, dashboard assets and denial of runtime source, SQLite and encryption-key HTTP paths. Full success requires HTTPS configuration and successful probes using a trusted certificate. Incomplete installations and missing HTTPS are blocked; wrong content, exposed private paths, redirects and transport errors fail. A pass describes this read-only HTTP scope only; it never certifies the release. It does not inspect on-disk permissions or prove public DNS, remote client access, ACME renewal or firewall policy.

Test apps are retained. Complete reversible app cleanup is unfinished: the current CMS deletion path does not remove its private sibling data directory, and WordPress SQL resources need explicit database/account cleanup. Do not use the website Delete action as an app QA reset or erase unknown resources manually. Failed installs stay available for inspection. No QA operation restores the VPS to a fresh OS baseline.

Automated coverage includes Owner/origin/strict-target/rate-limit/cache/audit boundaries, real loopback Host/redirect/TLS failure behavior, wrong product/domain/version rejection, private path exposure, service/installation blocking, redacted reports and concurrency recovery. The isolated container runs the production verifier against its real WordPress/PHP-FPM and CMS/Node/NGINX installs; absent public TLS stays blocked rather than being simulated as trusted acceptance. Other integration tests exercise login, CRUD and persistence separately. Systemd, rendered browser, target-host installs and restoration remain separate gates.
